# F02 Authentication Session Implementation Plan

> For agentic workers: use executing-plans to implement this plan task-by-task. Steps use checkbox syntax for tracking.

Goal: Implement the F02 backend login and logout contract with a BCrypt-verified demo account and immediately invalidatable Redis session token.

Architecture: AuthController maps HTTP requests to AuthService. AuthService validates the configured demo credentials, creates a cryptographically random opaque token, and delegates persistence to AuthSessionRepository; RedisAuthSessionRepository stores token-to-username sessions with a positive TTL. F01 frontend demo-session and all business modules remain unchanged.

Tech stack: Java 17, Spring Boot 3.4.4, Spring MVC, Spring Security Crypto BCrypt, Redisson 3.45.1, JUnit 5, MockMvc, Maven Wrapper, Docker Compose Redis.

Spec: docs/superpowers/specs/2026-08-25-f02-auth-design.md

## Global constraints

- F02 only adds POST /api/v1/auth/login and POST /api/v1/auth/logout; do not add protected business APIs or modify xiaou-frontend.
- The JSON response uses status and data, not the existing common R.code envelope.
- The demo username defaults to demo-pilot-pm; development password reads AECP_AUTH_DEMO_PASSWORD, then AECP_TEST_PASSWORD, then a non-production placeholder.
- Production configuration must require AECP_AUTH_DEMO_PASSWORD.
- Passwords and password hashes must not be logged, committed, or stored in Redis.
- Session keys use the configured prefix and positive TTL; logout deletes the Redis key and is idempotent for missing tokens.
- Preserve the existing user modification in AGENTS.md; do not stage or commit it.
- Run each test layer in order: unit tests, web/integration tests, then real Redis/application end-to-end verification.
